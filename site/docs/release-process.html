Preparing a public release

The repository is a development workspace containing the runtime together with tests, studies, artwork and examples. A public distribution needs a smaller and explicitly reviewed set of files, so the release build copies those files into a separate directory and records their contents in a manifest. Use that generated directory when preparing hosting rather than exposing the development workspace.

On this pageWhat the build producesValidation before a release candidateHosting a future public endpointExporting the public repositoriesDevelopment documentation

A successful build creates files for review without publishing a package or deploying a website. The package remains an unpublished alpha until publication is explicitly requested and completed. Build verification therefore describes the local artifact, not the availability or readiness of a public service.

What the build produces

After completing the validation steps below, run node scripts/build-release.mjs to recreate the ignored .local/release directory. The output location is fixed, and the build rejects symbolic links in its output-directory path so cleanup cannot be redirected to another directory. The resulting package, browser files and manifest serve different purposes in review and distribution.

.local/release/manifest.jsonReview and integrity inventoryVersion, relative path, byte size, and SHA-256 for every generated file

The public files exclude example applications, About-page candidates, third-party assets, benchmarks, tests and development directories such as research, review, handoff and lessons. The documentation includes only the named first-party demo scripts approved by the release checker. It may link to repository source or deeper development notes without copying those files into the public site, and asset licenses remain separate from the code license.

The browser runtime uses JavaScript ES modules, which run without compilation or minification. Your application can ask a bundler to resolve package imports and optimize the modules it uses, or a plain HTML page can import the generated file URLs directly. Three.js remains an optional dependency supplied by the application, while TypeScript declaration files describe APIs for editors and are not scripts to load in the browser.

An import map is an alternative way for an HTML page to map package names to module URLs. The generated import-map.json contains paths relative to the public root, so a page at another base URL must resolve or rewrite those paths before embedding the mapping. A browser does not load that external JSON automatically simply because it is next to the runtime files.

The manifest records each generated file's path, size and SHA-256 checksum. node scripts/check-release.mjs checks those records against the actual files, checks allowed paths and required entries, and verifies the package version and import-map targets. A checksum detects a change relative to that manifest but does not authenticate the publisher if an attacker can replace the manifest too.

The verifier also inspects the npm tarball independently of the pack command. It permits at most 16 MiB of compressed data and 64 MiB after decompression, then checks the USTAR archive headers, member boundaries and checksums used by this build. Links, extended headers, duplicate names, traversal paths, private paths and files outside the release list are rejected before the archive is accepted. Another tar dialect requires explicit support and review rather than assuming that any archive with a .tgz suffix is equivalent.

Finally, the verifier checks archived package metadata and every export target, compares the complete runtime and license byte-for-byte with the browser distribution, and requires the import map to match the archived exports. These comparisons make the npm and browser outputs reviewable as two forms of the same runtime rather than separate implementations.

Validation before a release candidate

Begin with npm ci so the development tools match the dependency lockfile. Run npm test, npm run lint, npm run docs:check, node scripts/build-types.mjs --check, npm run test:types, npm run check:package and npm run test:package-consumer to check native behavior, documentation, declarations and the packed package. If the API has changed, regenerate the corresponding declarations and inventories deliberately rather than suppressing a mismatch.

Browser and content checks exercise a different part of the release. Run npm run bench, npm run bench:visual, npm run verify:films, importer fuzzing and the full three-engine node scripts/browser-matrix.mjs campaign. Review failures, unsupported capabilities, partial runs and skips individually, because a skipped capability has not demonstrated successful rendering. The optional Three.js dependency must be supplied when that integration is part of the intended release check.

Review security findings and run npm audit before accepting the candidate. The native runtime has no required third-party implementation-library dependency, but development dependencies and optional integrations still require review. File-parser behavior, public output boundaries and resource limits need their own tests because dependency scanning cannot establish those properties.

Use the supported public imports to check both a packed consumer and the generated browser files. Review licenses, asset sources, documented limitations and optional-dependency behavior, then record any remaining device, accessibility, long-playback or real-content gaps. Tests and CI configuration establish only what has actually been observed, so keep those gaps visible in the release evidence.

Keep the version, changelog, inventory and validation evidence consistent before rebuilding. Run node scripts/check-release.mjs again against the finished result and review the concrete manifest and npm tarball before publication. The GitHub workflow uploads reports for native checks and Chromium/Firefox/WebKit fixtures even on failure, but its configuration cannot be reported as a green CI run until GitHub has executed it. Required checks and branch protection are separate repository settings.

Hosting a future public endpoint

Deploy only .local/release/public through the selected static host. The development server is intended for loopback inspection, and the repository root, .git, .local, dependency trees, test fixtures and study media must remain outside the hosted directory. The separation created by the build is the boundary to preserve when configuring the site.

Use HTTPS and correct JavaScript, CSS and font content types so browsers interpret each response as intended. Set X-Content-Type-Options: nosniff and choose a content-security policy for the actual application. The generated documentation needs its same-origin theme and interactive-example scripts, while another example application may require allowances for its selected renderers and assets.

If applications on other origins will import the runtime, configure CORS to allow the intended module requests. Prefer versioned immutable runtime URLs so a consuming page can keep a fixed implementation, and give mutable documentation or version pointers a shorter cache policy. The hosting configuration, public URL checks and cache verification must be tested at the actual destination rather than inferred from a successful local build.

Exporting the public repositories

The development repository stays private, so the public repositories receive only files copied out of a verified release build. Their history starts fresh and never includes the development history. After npm run build succeeds, run the export from the repository root.

npm run export:public

The command checks .local/release again and then writes two trees under .local/export/. The library/ tree is for prajwalsouza/ExplainerKit. It holds the npm package in package/, read back out of the verified archive so that it matches npm byte for byte, the website in site/, a README, the licence files, a GitHub Pages workflow that publishes site/, and release.json with the archive's SHA-256 and npm integrity values. The site/ tree holds only the website, with an empty .nojekyll file so that GitHub Pages serves it from the main branch as built, for the explainerkit.github.io site repository.

The READMEs for both trees come from release/library/ and release/site/, with the version and the website address filled in. Pass --site-url when the website lives somewhere other than https://explainerkit.github.io/. Before writing anything, the export scans every text file in both trees and stops if one names the development repository, contains a local machine path, uses the library's former name or carries an attribution line. It also stops on a file over GitHub's 100 MB limit and warns above 50 MB.

To place a tree in a local clone of its public repository, add --library or --site with the clone's path. The command first checks that the clone's origin is the expected public repository, then replaces everything in the clone except its .git folder. It never commits, pushes or publishes, so the clone's changes remain for review with git status before anyone commits them.

The export makes the website and the package public through different services, so their order matters. The guides tell readers to run npm install explainerkit and load the modules from a CDN that mirrors npm, so publish the exact verified archive with npm publish .local/release/package/explainerkit-VERSION.tgz before the website goes live. Publishing that file, rather than packing again, keeps the integrity value in release.json correct.

Before the first export, check that the generated browser files work outside the development tree. npm run test:distribution serves them from separate local origins in Chromium, Firefox and WebKit, and npm run test:distribution -- --three=.local/three adds the optional Three.js path after npm run setup:three has prepared it.

Development documentation

npm run docs:build creates the full local development site at .local/docs-site, including examples and their source/assets. node scripts/docs-site.mjs --public creates only the reviewed documentation under .local/release/public/docs, which is useful during editing but does not refresh the release manifest. Run the complete release build again before final verification or distribution so its checksums describe the finished files.

Formatting is checked separately from behavior. npm run format applies repository conventions and npm run format:check reports differences, while tests and snapshots still need to preserve the intended output. Treat a formatting pass as a reviewable source change rather than evidence that the runtime or documentation works.
