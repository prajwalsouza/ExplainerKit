How ExplainerKit is organized

An explanation often begins with a drawing and becomes interactive when a reader can change one of its values. ExplainerKit keeps those values and shapes in the same scene, so adding a slider or animation does not require rebuilding the construction as a different kind of object. The separate modules calculate values, arrange artwork or present the result while the scene continues to describe what is being explained.

This guide follows that separation from an individual shape to a browser view and then to the source folders. Read Getting started first if you need to display your first scene, or use the runtime API when you want a method signature. The module map and export inventory identify the public imports for the tasks described here.

Start with a small vocabulary

Creating a shape returns a handle, which is the JavaScript object used to change that particular shape. A circle's handle can set its radius or schedule a position change without losing the circle's identity. That stable identity matters when other parts of the explanation refer to the same object after an edit or data update.

A parameter stores a value that belongs to the scene, such as a speed controlled by a slider. A derived value calculates a result from one or more parameters, such as distance from speed and time, and a binding connects that result to a drawing property. An animation can change the same parameter, allowing the model and its visible result to stay connected whether the reader is watching or interacting.

Import these scene tools from explainerkit/core, then add another module when its calculation is needed. For example, a mechanism model can calculate the rotations of connected gears and bind those rotations to ordinary scene shapes. The model supplies the relationship between the gears while the scene supplies their identities and authored state.

The inventory lists each available export, including appearance and depth tools such as look and parallax. Use the task guide to understand an operation before relying on the export name alone, because the guide also describes its inputs, ownership and work limits.

Two uses of “data”

Scene inputs and numerical data transformations solve related but different problems. src/core/data.js stores values that belong to a scene and notifies the objects that depend on them when those values change. src/data/ provides calculations such as unit conversion, row transformations and scales that map values to chart positions, and those calculations can also run without a scene. Keeping the two roles separate lets an application reuse a calculation while deciding independently how to display its result.

Character builds and articulation

A ready-made character combines a visual design with a way of moving its parts. The designs and presets live under src/characters/builds/, while src/rigs/ contains calculations for connected joints and the adapters that bind their results to a scene. A cutout character may place artwork relative to a resting pose, whereas another skeleton may calculate positions from bone lengths and joint angles. Each tool keeps the representation its movement needs instead of forcing every character into one drawing format.

Assets and finished constructions

The runtime calculates and renders constructions without requiring the artwork, audio or datasets used by the examples. Keep those assets with the example or asset pack that uses them, together with their licenses and source credits. A finished watch therefore belongs in an example, while the reusable relation that makes two gears turn together belongs in mechanisms.

State and resource ownership

The owner of a value or resource is the part responsible for changing it and releasing it when appropriate. This distinction keeps a reusable calculation from starting an unexpected clock or network request, and it makes browser cleanup an explicit part of removing a view. The table summarizes the responsibilities that apply when the modules are combined.

Sampling a scene can use camera, geometry, appearance and layout helpers, but importing the core does not load characters, mechanisms, sound, players, renderers, browser adapters or editors. Calling scene.mount() requests the player and its renderer at the point where the application needs a browser view. The architecture check verifies these import boundaries so a model does not acquire browser responsibilities merely through an added dependency.

The native library has no required third-party runtime packages. When solid 3D rendering is needed, the application imports Three.js and passes that copy to the optional adapter. The renderer still supports only its documented features, so selecting Three.js or switching to SVG/Canvas requires checking the corresponding guide rather than assuming the representations are interchangeable.

Pure joint and mechanism calculations can run without a scene, player or renderer, although some helpers also import shared core definitions. Source-folder order is therefore not a loading rule by itself. When adding a dependency, check both what it loads and whether that responsibility belongs in the importing module.

Use the shared color tools

HSLA describes a color through hue, saturation, lightness and alpha, where alpha controls opacity. Supply hue in degrees, saturation and lightness as percentages, and alpha in the range 0–1. The shared color module generates, adjusts and mixes those values so procedural palettes can follow the same conventions throughout the library. Convert to hexadecimal or RGBA when a renderer or data buffer requires red, green, blue and alpha channels.

HSL lightness is an authoring coordinate rather than a measurement of perceived brightness. Equal changes in its numeric value do not necessarily look equally large, and contrast checks still need relative luminance. Calculations that represent light intensity can instead use linear RGB. The existing RGB interpolation defaults remain in place, while callers explicitly choose HSLA mixing when that is the intended artistic relationship.

Compatibility is deliberate

Use the package import named in the module map, because an implementation file under src/ is not automatically a public npm entry. Library source files import their owning implementation directly, and the repository's compatibility tests record the public interfaces they check. These checks protect callers' function and object identities while allowing implementation files to be organized by responsibility.

A public import must be treated as part of the package interface when changing code. Do not duplicate an implementation behind another name or remove a path as incidental cleanup. The architecture and compatibility checks verify the relationships between modules, while behavioral tests are still needed to check what those modules do.

Development repository and public release

The development repository also holds examples, measurements and source records that are not runtime dependencies. In it, src/ contains the library implementation and public-entry forwarding files, while docs/ contains user guidance together with separately identified proposals and research. examples/ holds authored applications, and assets/ holds the content they use with its license information.

The tests and benchmarks exercise behavior and collect measurements rather than provide package functionality. Development scripts build and verify the distribution, and generated artifacts remain working outputs. Keeping these materials in the repository makes them available to contributors without making them part of a public website.

The npm package contains runtime source, TypeScript declarations, package metadata, the license, README and changelog. The release build enforces that file list and creates a separate set of files for public hosting. Follow the release process to build and verify those files instead of serving the repository or its loopback development server as a public site.

How to add or change a capability

Begin by deciding which existing module should own the feature and which other parts only need its result. Document the inputs, output, permitted changes, processing limits and cleanup before choosing another public entry. Calculations should remain usable without a browser when they do not need browser resources.

Use the shared color, input-validation and noise helpers rather than introducing a local variation of the same behavior. Add a separate public import when an application benefits from loading that feature independently, and accompany it with a small example, precise limits and reviewed TypeScript declarations. This makes the feature discoverable without placing its implementation behind several unrelated names.

Check a real change to the construction as well as its initial result. Replacing a palette should leave a solver's result intact, changing a renderer should preserve authored object identities, and changing a gear ratio should not replace the player. These scenarios test whether the responsibilities described above continue to hold when the application is edited.

Run node scripts/check-architecture.mjs to check imports and node --test tests/modules/restructure-compatibility.test.js to check shared function/object identities and the documented package interface. Package-consumer, type, behavioral and browser checks then exercise the result from a caller's perspective. Passing the structural checks alone does not establish production readiness or usability.
