Security boundaries

ExplainerKit can read supported files and turn their contents into geometry, but those file inputs are not treated as application code. The importers do not execute SVG scripts, open external SVG resources, run font hinting programs or automatically fetch glTF dependencies. Application callbacks and custom renderers are different because they are JavaScript that runs with the application's permissions, so only provide code you trust.

Untrusted input

A file's byte size is only part of the work an import may require. A compressed font can expand substantially, and a small mesh can be instanced many times, so the importers also limit nesting, output and the total processing needed to produce it. Those checks include WOFF decompression, font kerning/variation/composite processing, XML attributes and repeated glTF index visits. When a limit is reached, report the returned error to the user rather than automatically retrying with unlimited work.

Per-import limits do not cap the cost of an entire application session. Your application must also control how many imports run together, how often a job can repeat and when to cancel or time out work. Use a worker for large user-supplied imports when the corresponding work would otherwise block interaction on the main page.

For glTF, maxIndices limits the total number of triangle-index visits, including visits caused by repeated instances. Its default is 600,000 and it can be configured up to 6,000,000. This processing limit is separate from the counts of unique vertices and edges, so increasing one does not remove the others.

Colors follow a similarly explicit input boundary. The shared parser accepts hexadecimal colors, supported names and numeric HSL/HSLA values, but does not evaluate URLs, CSS variables or arbitrary expressions. Renderers receive the normalized paint data produced by that parser. Use the color module to retain those checks instead of asking the browser to interpret another color-string format.

Browser ownership

Players and renderers own browser resources that need to be released when their view is removed. Call their disposal methods as part of the application's cleanup, and keep resource loading, media playback and optional adapters as explicit application choices. In particular, Three.js must be supplied by the application because the core does not download it or switch to it as an implicit fallback.

Unsupported operations are reported as errors rather than implemented by running supplied markup or discarding security-relevant fields. That refusal preserves the boundary between supported data and executable application code. It does not make trusted callbacks safe to accept from an unknown author, because those callbacks are outside the importer's data-validation boundary.

Hosting the library files

When you serve ExplainerKit's modules from your own site, publish only the files you mean to offer, such as a copy of the package's src/ folder. Keep project roots, .git folders, dependency trees, environment files and local scratch files out of the hosted directory, because a static host serves whatever that directory contains.

Use HTTPS, and send JavaScript, CSS and font files with their correct content types so that browsers interpret each response as intended. The X-Content-Type-Options: nosniff header stops a browser from guessing a different type. Choose a content-security policy for the actual page, and allow cross-origin requests through CORS only when pages on other origins are meant to import your copy.

ExplainerKit's development repository includes a local server for inspecting pages during development. It accepts only loopback hosts and restricts which folders it serves, but it is not a server to deploy publicly.

Verification and disclosure

Run npm audit, importer/security tests, packed-package consumer checks and browser fixtures against the source you intend to release. These checks cover different risks, and the development review records the boundaries and adversarial examples that were actually examined. Neither a passing suite nor an empty dependency advisory list certifies that every use of the library is secure.

If you find a vulnerability, report the affected version, input format and a bounded reproduction privately to the repository maintainer before publishing exploit details. Include enough information to reproduce the failure without attaching credentials or private user files, so the issue can be investigated without introducing another disclosure.
