Guide / Documentation

What works and what remains

ExplainerKit is an alpha JavaScript library for visual explanations that people can explore in a browser. A scene keeps the shapes together with the values that control them, allowing the same construction to be animated or changed through reader input. This page describes what that implementation can do and the limits to consider before choosing it for a project.

Start with the part you need

Use Getting started to display a scene through npm or plain HTML, then choose a construction tool from the module map. The runtime API explains the scene and shape methods used by those tools, so a specialized module can extend the same drawing instead of replacing its basic model.

Import explainerkit/core to create the scene and its basic shapes, then add calculations for the subject being explained. For instance, explainerkit/mechanisms can relate gear rotations while explainerkit/characters can apply a pose to a character. Their results connect to the ordinary scene properties described in the library layers guide.

SVG and Canvas render ordinary 2D scenes without a rendering-library dependency. When a scene needs solid, lit 3D objects, the optional adapter uses a Three.js module supplied by the application. Importing the core does not acquire that dependency, so choose the intended renderer and follow the optional-dependency test commands when evaluating that path.

How the parts work together

A scene stores the construction rather than the browser view. It owns shape identities, data, parameters and authored motion, and sampling those relationships produces a frame for a chosen time. Because sampling does not require replaying every earlier frame, the same scene can support seeking, offline capture and interaction.

A model calculates geometry or values, and a renderer turns a validated frame into a picture. A player adds the clock, controls, resize handling and cleanup needed to present that picture in a browser. Scroll stories or media can supply the player's time, and HTML/text bindings can follow it, without making every model responsible for another animation loop.

The application supplies the content and decides what observations or interactions mean. It chooses resources, provides trusted callbacks and connects user input to scene parameters, while scientific assumptions, example stories and artwork remain outside runtime policy. The architecture guide explains how that separation keeps a reusable calculation from unexpectedly owning browser resources.

Each renderer accepts a defined representation of the construction. SVG/Canvas draw 2D geometry, WebGL2 draws its supported point and line buffers, and the optional Three.js adapter handles its solid-geometry subset. Project a 3D model into a supported 2D form before passing it to a 2D renderer, and check the chosen representation's limits when switching renderers because feature support and pixels need not be identical.

Limits to plan for

Shapes and appearance

Outline operations determine which regions remain after shapes are combined or cut. They support concave outlines and holes by approximating curves with line segments within a chosen tolerance, while partition tools produce convex pieces. The operation does not decide which new piece retains an original object's meaning, and stroking adjacent cut pieces can leave seams. The shape-operations guide explains those geometric and identity limits.

A morph changes an outline by matching points between its starting and ending contours. The tools support single outlines or named sets of contours, with controls for winding, starting points and landmarks so the intended correspondence can be supplied. Colors may interpolate with premultiplied alpha, which weights color channels by opacity, and unmatched objects can fade explicitly.

Those choices do not infer the intended meaning of arbitrary objects or guarantee that every intermediate outline stays valid. Morph safety and shape keys add checks and a defined order for supported deformations rather than an unrestricted mesh-deformation system. Use those checks when an invalid intermediate shape would change the explanation.

Reusable components preserve named parts across instances, while a B-spline lattice bends artwork through a grid of control points. Placement helpers can distribute objects in a grid, around a center or along a path. Automatically exposing every component parameter, providing general reusable action libraries and generating arbitrary changes in connectivity remain work beyond those implemented operations.

Appearance effects operate on a bounded amount of rendering work, so blur, glow, masks, shading, textures and exposures have transform and raster limits as well as input settings. They do not supply an arbitrary filter graph, HDR processing or physical lighting simulation, and image/luminance masks are unsupported.

The simple-shadow tools instead project supplied vertices from a point light onto a declared plane, with separate constraints for wall shadows. They need the relevant geometry from the application rather than discovering it from an image or solving every light interaction in the scene.

Motion, joints and characters

Joint posing can begin with angles or with a target that a limb should reach. The 2D tools support branched skeletons, several weighted or prioritized targets and control over the end-joint angle or bend direction, together with named attachments, weighted artwork and curve rigs. Iterative solutions report remaining error and convergence so the application can distinguish a close approximation from an exact reach.

These tools do not supply general force/contact/collision simulation, mechanisms with cyclic constraints or automatic motion retargeting. Keeping every length fixed while posing a chain along a curve also remains outside the implementation. Read the specific rig guide when those requirements affect whether a solution is usable.

The two-bone 3D solver extends the target-reaching task to a defined three-dimensional calculation, and the lightweight biped tools use explicit pose and movement rules. Those APIs can help stage a character without becoming a general 3D character-rig or physics system. The rig guide and biped guide explain the different inputs and limits of each approach.

Springs and inertia calculate motion at a requested time, while seeded particle schedules make repeated sampling reproducible. Coherent value noise supplies smooth variation, and the lag, jiggle and squash/stretch helpers add their documented responses within processing limits. Squash/stretch preserves area under its stated assumptions. These are visual motion models rather than an arbitrary stateful physics or fluid solver, and a chosen noise pattern does not by itself model a physical process.

A mechanism model relates the motion of connected parts, such as gear pitch, a no-slip rolling object, a slider-crank or a belt and pulley. The implemented 2D relations have no cyclic dependencies and calculate movement rather than forces, torque or contact. They can explain a kinematic relationship but do not certify a design for mechanical construction.

The character toolkit provides cut-out artwork with joints and limb controls, including rubber-hose and two-bone limbs, faces, nine mouth shapes, moods and gaze. Its planted-foot walks and shared pose tools work with 16 CC0 starters, while the character pack supports editable SVG import/export and ZIP distribution. The planar starters support left/right facing and flat-ground walks, with full turnarounds, quadruped gait and large-crowd performance remaining outside the established scope.

Text-based speech supplies the default mouth timing, while character.lipSync can import audio-aligned cues prepared by an external tool. Importing those cues does not recognize speech or validate their alignment against the recording. Blink and eye-dart schedules stay reproducible through 24-hour scene time, and bun/bird-tail follow-through is implemented within its documented limits.

Native scene shading is an explicit shade:true choice that retains the default appearance unless requested. Other appendages and a wholesale default-shading choice require their own work and validation. The character controls guide explains those options. The timing measurements recorded during development cover only the measured cases and do not promise device-wide performance.

Layout, views and 3D

Layout tools work from the objects, relationships and available space supplied by the application. Grid, stack and adaptive plans can rearrange supported content, declared groups can remain together and grouping tools can report cues such as proximity or connectedness. Text sizes are estimated unless measurements are supplied, and neither route guarantees that every possible scene fits without overlap.

Labels and annotations need actual text, obstacles, priorities and an available placement region. The planner cannot infer which objects the explanation must show simultaneously or decide when narration should wait. Those decisions remain with the author and determine whether a proposed arrangement communicates the intended comparison.

Camera and zoom calculations use finite floating-point coordinates, so their limits matter when scenes span very different scales. Nested views can shift their local origin to keep useful precision, and detail-level transitions switch between authored representations at different zoom distances. These visibility changes do not automatically stream or evict assets. A deliberate camera shot keeps its shared spatial relationship rather than independently restacking the objects it follows, as described in deep zoom.

A projected 3D surface can report which side faces the camera so the drawing can fade its far side or reorder objects by depth. That test does not remove every hidden line or correctly order all intersecting surfaces. The core also does not supply physically based materials or AR registration, and optional Three.js, WebGL point/line buffers and ordinary 2D paths keep their separate rendering contracts.

Text and imported assets

An HTML binding connects scene values to an element already present in the document. The text tools can then split words or graphemes and reveal them at a chosen time, using the same player instead of another animation system. Browser setup and cleanup remain explicit, and these tools do not provide general CSS animation or rich-text layout.

Importers read their supported data into editable geometry without treating a file format as executable application content. SVG import does not run scripts or acquire external resources, while the font importer can read TrueType outlines from TTF or WOFF together with pair kerning and variable axes. WOFF2/CFF, glyph-substitution tables, combining-mark positioning and bidirectional text shaping are unsupported.

Static triangle geometry from glTF/GLB can use explicitly supplied buffers, but texture, skin and animation decoding are not provided. The font guide and importer links in the module map describe the format and processing limits to check before choosing a source file.

Data, inputs and saved projects

A keyed data source uses an identifier to keep the same object associated with a surviving row after replacement or reordering. Updates validate the next result before adoption, and scales, summaries, bins, stacks, units, plots and axes operate on the supported values. Persistent source provenance, general schema migrations, portable formulas and broader chart/diagram systems remain work beyond that data-to-drawing layer.

Live input adapters acquire observations only after explicit startup and must be disposed when no longer needed. Pointer, file, sensor, camera and microphone acquisition can update scene parameters, but video analysis, general stream joins, cross-device replay and AR tracking/hits/anchors are outside the implemented acquisition tools. Check permission and sensor behavior on the actual physical devices because acquisition support does not establish every device integration.

A project recipe stores the supported construction in a form that can be saved and rebuilt, with bounded undo/redo for edits. It does not serialize every runtime feature, application callback or browser resource, and it does not supply a persistent relationship graph or durable replay of arbitrary events. The project guide identifies the subset that can be represented and the limits applied to it.

The asset queue preloads raw bytes so an application can prepare for upcoming content without making scene sampling perform network work. Callers supply allowed origins, integrity settings and limits for concurrency, eviction and retained bytes. The queue does not decode the data or impose an exact limit on total JavaScript heap or network usage, and it is not a production exporter. See story and asset delivery for the ownership needed around those requests.

Playback, accessibility and production

A scroll story maps position to authored time through acts and holds, with optional smoothing, snapping and a sticky stage. It supports reverse scrolling and resizing, can update acts and duration without detaching, and can use authored still frames for reduced motion. Native sticky-positioning rules still constrain the page, so validate the complete story with its actual content rather than treating a working adapter as a finished long-form experience.

Players and films provide their supported descriptions, captions and controls while presenting the scene. When audio or video should drive playback, the media adapter synchronizes that existing clock rather than creating another scene timeline. Local export tools can capture reproducible PNG/video frames at 1080p and 4K, while the offline mixer processes its supported audio data. Recording narration or music, editing several footage sources, broader audio workflows and final editorial review remain production tasks for the application.

Automated accessibility checks, keyboard controls and reduced-motion behavior exercise specific states of a view. They do not establish physical-device performance or VoiceOver/NVDA usability for the finished explanation. Test with the input methods and assistive technology the audience uses.

What still needs validation

Validation needs to follow a complete explanation through data changes, resizing, dragging, seeking, renderer changes and resource failures. Combinations need attention because an individually supported feature may behave differently alongside measured labels, important comparisons or layout changes during motion. Live-source cleanup, saved projects, production media and long sessions also need checks with the actual application rather than only a small isolated fixture.

Native tests compare calculated values, object identity and resource limits, while browser fixtures inspect actual pixels, interactions, cleanup and layouts. Optional Three.js checks require a supplied dependency, and a missing-dependency skip does not show that rendering succeeded. Apply a report only to its recorded source revision, environment and run, then rerun relevant checks after changes.

The release build creates a local set of reviewed files without publishing them. Follow the release process to check the npm package, browser output and manifest before any separately requested deployment or publication.
