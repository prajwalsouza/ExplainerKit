# Use ExplainerKit with AI agents

ExplainerKit has no other API besides its JavaScript modules, so an AI agent uses the library by writing code that imports it. Agents tend to miss most of the library for three reasons. No model has seen ExplainerKit in its training data, the package has more than sixty imports, and an agent cannot see what its code draws. This page describes the tools that close those gaps and how to connect them. The tools are an index for finding capabilities, Agent Skills, a Model Context Protocol (MCP) server, a command-line equivalent and an evaluation.

All of these files are generated from the package or tested against it. `npm run agents:check` fails when the index or skills no longer match the exports, guides and recipes, and `npm run test:agents` runs every recipe in a browser.

## What an agent needs

An agent writing an explanation has to answer three questions. It has to find out whether the library already does the job, learn the exact names that the code needs, and check that the result looks right. Each tool below answers one or more of those questions.

| Tool | Where | What it answers |
| --- | --- | --- |
| Capability index | `llms.txt`, `agents/catalog.json` | Which import does a task, which guide explains it and which names and option values exist. |
| Recipes | `agents/recipes/` | A complete, tested module to start from for a common task. |
| Agent Skills | `agents/skills/` | The same knowledge, loaded automatically by agents that support skills when a task matches. |
| MCP server | `agents/mcp/server.mjs` | Search, guides, recipes, name checks and a headless preview, called as tools. |
| Command line | `agents/cli.mjs` | The MCP tools for agents that can run shell commands but cannot use MCP. |
| Evaluation | `agents/eval/`, `scripts/agents/eval.mjs` | Whether the tools change what agents actually build. |

## The capability index

`llms.txt` at the repository root is a compact Markdown index in the style proposed at llmstxt.org. It lists every canonical import with its purpose and guides, every recipe, and the fixed vocabularies that agents most often guess wrongly. These include the named easings, the entrance styles, the properties each shape accepts and the preset effects. It ends with common mistakes, such as writing the SVG property `textAnchor` where ExplainerKit uses `align`. An agent that reads only one file should read this one.

`agents/catalog.json` holds the same information as data, with every export name, guide headings and search keywords. The MCP server and command-line tool search it. Both files are generated by `npm run agents:build` from `package.json`, the [module map](modules/index.md), the guides it links, the recipes and the source of the vocabularies. Two inputs are written by hand in `agents/areas.mjs`. They are the grouping of imports into skill areas, with plain-language search phrases for each module, and the list of common mistakes.

## Recipes

A recipe is a complete ES module for one common task, such as a scene that plays, a slider that drives the drawing, a bar chart, a scroll story, camera shots, gears, a character or a beat grid for music. Each recipe renders into `<div id="stage">` and exports the player that `scene.mount()` returns, so tools can seek it to exact times. A comment block at the top gives its title, task, imports, search keywords and guide. `npm run test:agents` runs every recipe in Chromium at its capture times and fails on any error, on an empty stage or when the captures do not change.

Add a recipe when agents repeatedly need a task that the existing ones do not cover. Write the comment block, run `npm run agents:build`, then run `npm run test:agents`.

## Agent Skills

A skill is a folder with a `SKILL.md` file that an agent loads when its description matches the task. The generated skills are one router skill, `explainerkit`, and seven area skills covering scenes, motion, stories, data, camera and 3D, characters and machines, and sound and music. Each area skill lists its imports with their exports and guides, includes the code of its recipes and ends with instructions to check the result with the preview tool.

Agents working in this repository find the skills through the `.claude/skills` link to `agents/skills`. To use them in another project, copy or link the folders into that project's `.claude/skills` or into `~/.claude/skills`. The design process skills from `explainerkit/design` are exported separately by the documentation build.

## The MCP server

The Model Context Protocol lets an agent call tools that a local program provides. ExplainerKit's server is a single Node script with no dependencies. It reads JSON-RPC messages on standard input and writes replies on standard output. In this repository, `.mcp.json` registers it for Claude Code, so a session started here offers the tools after you approve the server. In another project that has the package installed, register it with the command below, or add the same command to your client's MCP configuration.

```sh
claude mcp add explainerkit -- npx explainerkit-mcp
```

The server offers nine tools. Its instructions tell the agent to use them in the order below.

| Tool | Use |
| --- | --- |
| `find_capability` | Rank modules and recipes for a task described in plain words. |
| `list_modules` | List every import with its guides, grouped by area. |
| `read_guide` | Read a guide, or one section of it, by path or by import name. |
| `get_recipe` | Return a recipe's code. |
| `lookup_export` | Find which import exports a name and show its TypeScript declaration, or suggest a near match. |
| `describe_shape` | List the properties a shape accepts, with the easings and entrance styles. |
| `check_code` | Report imports and names that do not exist, unknown shape properties, unknown easings and effects, and known mistakes. |
| `preview` | Run a module in headless Chromium and return screenshots, console output and errors. |
| `analyze_music` | Analyse a local audio file with `explainerkit/music` and summarise its tempo, sections and events. |

`preview` is the tool that lets an agent see its work. It serves the module with an import map that resolves `explainerkit` imports to this package's source, then loads it in a page with `<div id="stage">`. If the module exports `player` or a `seek(seconds)` function, the tool captures exact scene times. Otherwise it waits for real time to pass. A capture is reported as empty when the stage has no drawing, and every page error and failed request is returned. The page can load only the package's `src/` and `assets/` folders. Preview needs Playwright and a Chromium browser. It uses `EXPLAINERKIT_CHROMIUM` when that names an executable, then Playwright's own download, then common system installs of Chromium and Google Chrome. Set `EXPLAINERKIT_CHROMIUM` when the browser is elsewhere.

`check_code` runs without a browser and catches most invented names. It cannot see every option, because many functions validate nested options only when they run, so an agent should still run `preview`. `read_guide` can read only `docs/`, `README.md` and `llms.txt`. An installed package includes the module guides in `docs/modules/` and the main guides they link to, such as getting started, the runtime API, error codes and this page. Other documents, such as most research notes, stay in the repository, and for those the tool explains where to read them online. `analyze_music` reads WAV files directly and decodes other formats with ffmpeg when it is installed.

## The command line

Agents that run shell commands but have no MCP client can use the same tools through `agents/cli.mjs`. Run the command from the ExplainerKit repository or the installed package folder. `preview` saves its screenshots as PNG files and prints where they are, so the agent can open them.

```sh
node agents/cli.mjs find "pulse a dot on the beat of a song"
node agents/cli.mjs recipe music-grid
node agents/cli.mjs check my-scene.js
node agents/cli.mjs preview my-scene.js --times 0.5,2 --out shots
```

## Measure whether it helps

`agents/eval/tasks.json` holds fifteen tasks written the way a person would ask for them, each with the capabilities a good solution should use. Three tasks are marked `heldOut`. No recipe covers them, so they measure whether an agent finds an unfamiliar module on its own. Ask an agent to write one module per task into a folder, then score one or more folders.

```sh
node scripts/agents/eval.mjs runs/without-tools runs/with-tools --json report.json
```

The score reports how many solutions exist, the share of expected capabilities that the code uses, how many render without errors and with a visible stage, how many export a player for exact seeking, and how many definite problems `check_code` finds. Capability use is a text match on import paths and names, so it shows whether an agent found a feature rather than whether it used it well. Look at the screenshots as well. The results apply to the agents, models and instructions used in that run. The [pilots](research/agent-tooling-pilot.md) found that a strong model used every expected capability with or without the tools, and that the tools cut tokens and time for every model tested. A small model working from the installed package under a budget missed about half of the modules with or without the tools, so the tools alone do not solve that case.

## Keep the tools current

Run `npm run agents:build` after changing exports, the module map, a guide's title or headings, a recipe or `agents/areas.mjs`. `npm run docs:check` includes `agents:check`, and the fast tests compare the generated files, check search results for typical requests, check that `check_code` finds known mistakes without flagging any recipe, and exercise the MCP protocol. `npm run test:agents` needs a browser and runs the recipes and preview error handling.
